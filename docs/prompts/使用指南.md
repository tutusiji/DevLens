# DevLens 提示词使用指南

## 提示词文件

主提示词：`devlens-mvp-prompt.md`（同目录下）

这份提示词是**自包含的**，已嵌入：
- v1 项目验证过的算法规格（7维能力加权公式、Bus Factor、Git行为熵分析、4级身份匹配）
- v2 项目验证过的页面结构（8个页面、shadcn/ui 暗色主题、recharts 图表）
- ChatGPT 文档验证过的架构方向（三位一体评估、Agent分层、Pipeline编排）
- 完整的数据库 schema（10张表）、API 设计、目录结构

## 不同 AI 的使用建议

### ChatGPT (GPT-4o / GPT-4-turbo)
- **直接全量粘贴** `devlens-mvp-prompt.md`
- 上下文窗口够大，能一次理解全部要求
- 输出可能超长，记得它会在结尾说"接下来输出 X"，你回复"继续"
- 代码质量高，算法实现准确

### Claude (Sonnet 3.5 / Opus)
- **直接全量粘贴**
- Claude 擅长长文档和代码，对算法规格理解最准
- 会严格按公式实现，不会自己发挥改系数
- 文件多时分段输出，回复"继续"即可

### DeepSeek V3 / R1
- **直接全量粘贴**
- 代码生成能力强，免费额度够用
- R1 推理模式对算法实现更准，但速度慢

### 通义千问 / 文心一言
- 上下文窗口可能不够，建议**分段喂**
- 先喂"角色+背景+技术栈+目录结构"部分，让它理解全局
- 再逐个喂"算法 1~7"让它生成对应 service
- 最后喂"前端设计"生成页面

### Gemini 1.5 Pro
- **直接全量粘贴**，上下文窗口 100 万 token 够大
- 但代码细节可能不如 Claude/GPT 严谨，生成后建议用 Claude 复核算法部分

## 如果 AI 输出不完整（常见情况）

提示词要求生成的文件很多，几乎不可能一次输出完。处理策略：

1. **第一次回复**：让 AI 先生成 README + 后端核心（main/config/database/models/services）
2. **第二次回复"继续"**：生成 API 路由 + workers + alembic
3. **第三次回复"继续"**：生成前端页面
4. **第四次回复"继续"**：生成 Docker + Makefile + docs

如果某个文件 AI 说"略"或"类似上面"，回复：**"请不要省略，完整输出 X 文件的全部代码"**

## 关键检查点（生成后必查）

AI 生成的代码一定要检查这几项，这是最容易出错的地方：

### 必查 1：7 维能力模型系数
```python
# 必须是这个系数，不能变
code_quality = ai_review_score*0.35 + lint_pass_rate*0.15 + (100-bug_introduction_rate)*0.30 + code_survival_rate*0.20
```
AI 容易自作主张改系数或改维度名。

### 必查 2：Bus Factor 阈值
```python
if cumulative >= total * 0.8:  # 必须是 0.8，不是 0.5 或 0.7
    return i + 1
```

### 必查 3：节奏熵归一化
```python
regularity = 1 - (entropy / math.log2(24))  # 必须 log2(24)，不是 log2(12) 或 ln(24)
```

### 必查 4：pipeline.py 不能有 TODO
8 个阶段必须都有实现。如果 AI 写了 `# TODO: implement`，回复：
**"pipeline.py 的阶段 X 不能是 TODO，请完整实现，调用对应 service 的方法"**

### 必查 5：assessments API 不能是空壳
```python
# 错误（AI 常犯）：
@router.get("/project/{id}")
async def project_assessment(id):
    return {"scores": {}}  # 这不行

# 正确：必须从 dev_skill_vectors 表查真实数据
```

### 必查 6：前端不能用 mock
检查 `app/page.tsx` 等页面，如果 import 了 mock 数据，回复：
**"前端必须调用 /api/v1 的真实接口，请用 fetch 封装 API 客户端，不要用 mock 数据"**

### 必查 7：项目评估与 AI Review 治理

项目评估详细规范见 [`../架构设计/项目评估与AIReview架构设计.md`](../架构设计/项目评估与AIReview架构设计.md)。生成或实现项目分析能力后，逐项确认：

- 项目评分能够回溯到原始指标、规则结果与证据，LLM 文案不能单独决定评分；
- 每条洞察包含类别、严重性、置信度、文件/符号/行范围、来源、影响、建议和治理状态；
- 配置扫描不会输出或持久化明文机密，传给模型的内容已脱敏；
- 中间件和环境识别标记“确认使用 / 疑似引用 / 仅依赖存在”，并展示判定依据；
- 修复项能关联洞察，并通过提交、测试或重新扫描验证 `resolved`；
- 项目、团队与人员关联只使用经过证据化、去重和治理的可解释工程信号。

## 远程仓库接入边界

当前前端接入页支持 GitHub、GitLab、Gitea、Bitbucket 及通用 Git URL 的导入表单，并保留本地路径模式。需要明确：

- 前端提交远程地址、分支和本次请求使用的临时 Token，但当前仓库没有 backend，Mock 模式不会真正 clone 远程仓库；
- 真正的 clone、鉴权、Git log/blame、浅克隆、超时、重试和分析 Worker 必须由后端完成；
- Token 不得写入 URL、日志、项目实体、仓库列表或分析结果，后端应只在任务生命周期内使用并按安全策略清理；
- 真实 provider 集成需要处理 GitHub/GitLab API 限流（429）、权限错误、仓库不存在、分支不存在和网络超时；
- 前端的 `runId`/状态轮询契约用于后续接入真实 Worker，不代表当前已经完成远程仓库克隆。

## 进阶用法

### 想要更精简的版本
如果觉得提示词太长，可以删掉"算法 1~7"里的代码示例，只保留公式描述。但这样 AI 生成的代码可能不严格对标。

### 想要分语言生成
把提示词里的技术栈改成：
- 后端 Node.js (NestJS)：把 Python 算法翻译成 TS
- 后端 Go (Gin)：注意 tree-sitter/LLM 生态弱

但**不推荐**，Python 的 AI 生态最好，算法资产最完整。

### 想加 GitLab/GitHub API 集成
在"算法 3：Git 行为分析"后面加：
```
### 算法 3.5：远程仓库集成（第二迭代）
- GitLab API：GET /projects, GET /projects/:id/repository/commits, GET /merge_requests
- GitHub API：GET /repos/:owner/:repo/commits, GET /repos/:owner/:repo/pulls
- 鉴权：Personal Access Token
- 限流：处理 429，指数退避
```
